# JEB unit 간 전역 우선 수집

manifest-first는 이제 모든 JEB unit의 후보에서 종류별 상위 N개를 선택한다.
Manifest 클래스 일치 → package 경계 일치 → 나머지 순서이며 같은 순위는
원래 unit 순서/항목 순서를 유지한다. 시그니처가 같아도 unit 출처를 합치지 않는다.
native 정책의 기존 unit별 수집 순서는 바꾸지 않았다.

클래스 전체 → 필드 전체 → 메서드 전체 순서로 한 종류씩 선택/저장한다.
각 종류에서는 우선순위 순서대로 바이트를 계수하므로, 앞 unit의 낮은 우선순위
항목이 뒤 unit의 높은 우선순위 항목보다 먼저 그 종류의 바이트를 소비하지 않는다.
합산 바이트 한도가 클래스/필드에서 소진되면 뒤 종류가 전부 제외될 수 있다.
종류 간 예산 예약이나 우선순위 비교는 아직 없다.

후보 heap/선택 목록은 종류별 제한 N에 비례한다. 전체 시그니처를 보관하지 않지만
각 종류의 후보를 모두 순회한다. 단일 문자열·JEB 기본 데이터·실행시간/RSS의 상한은
보장하지 않는다. 기존 개수·인덱스 바이트·본문 바이트 제한과 제외 진단을 유지한다.
선택 시작/완료 단계 계측을 추가했다. bridge/helper 해시가 캐시 키에 포함되어
구형 unit 내부 정책의 캐시와 섞이지 않는다.

신규 결과 capabilities는 global across JEB units를 기록한다. GUI는 이 값을
읽어 전역 정책을 표시하며 기존 within each JEB unit 결과는 기존 범위를 표시한다.
구형 결과를 새 정책으로 재해석하거나 수정하지 않는다.

## 검증 범위

신규 8개 테스트: 뒤 unit의 우선 클래스, 안정 순서/중복 출처, native/manifest-first
각각의 1바이트/250바이트/충분한 예산, 종류별 누락 수, 원래 unit에 연결된 본문 내보내기,
새 정책/구형 정책 GUI 구분. 실제 bridge index 함수 AST를 추출해 합성 unit 두 개로
실행하므로 별도의 알고리즘 복제본을 시험하는 것은 아니다.
기존 실제 JEB/Jython fixture 우선 선택 시험도 통과했다.
전체 회귀 **663 passed (93.86초)**, 실제 JEB 통합 15개 포함.
본문의 원래 unit 연결 검사를 보강한 신규 8개 테스트도 별도로 재통과했다.
여러 실제 JEB unit을 가진 APK의 성능/메모리 검증을 완료했다는 의미는 아니다.
amoremall은 DEX 파일 5개가 JEB unit 하나로 병합되므로 다중 unit 검증 사례가 아니다.
이번 단계에서는 사용자 APK 재분석이나 사용자 설정 변경을 하지 않았다.

## 호출 대상 본문 확보 판단

현재는 호출 대상 자동 추가를 하지 않는다. 단순 추가는 선언/본문 제한을 초과하거나
이미 선택한 Manifest 근거를 밀어낼 수 있고, 같은 시그니처의 여러 unit 및 가상 호출은
단일 대상으로 확정할 수 없다. 후속으로 저장 호출의 대상 본문 누락/모호성을 계측했다
(`CALL_TARGET_COVERAGE.md`).
그 뒤 별도 예약 예산, 깊이, 순환 차단, unit 출처 검증을 갖춘 제한적 확장을 검토한다.
전역 선택만으로 모든 호출 대상·상속·콜백이나 실행 진입점을 확보했다고 판단하면 안 된다.
