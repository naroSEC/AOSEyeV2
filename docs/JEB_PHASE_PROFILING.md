# JEB 선언·응답 단계 계측 (2026-10-04)

목적은 대형 APK에서 마지막 완료 단계를 구분하는 것이다. 강제 GC, heap dump,
실행 앱 연결 없이 인덱싱의 다음 지점을 기록한다.

- artifact 처리 전/후와 DEX 처리 완료
- DEX별 선언 수집 시작 및 클래스·필드 목록 완료
- 메서드 선언 10,000개마다 진행과 본문 내보내기 바이트 한도 도달
- 인덱스 구성 완료와 응답 JSON 직렬화 시작/완료

PhaseTrace는 Java Runtime의 used/committed/max heap, GC MXBean의 누적 횟수/밀리초,
해당 시점의 선언/내보내기 수를 JSONL에 기록하고 매번 flush한다. 경과 시간 대신
epoch timestamp를 사용해 다른 writer의 체크포인트도 비교할 수 있게 했다.
벽시계 변경이 있을 수 있고 heap used는 살아 있는 객체의 정확한 retained size가 아니다.
단계 사이에는 JEB 백그라운드 작업과 GC도 있으므로 차이를 해당 단계만의 할당량으로
해석하면 안 된다. 누적 GC 시간도 GC 구현별 의미가 다르며 CPU 시간과 같지 않다.

index writer는 최대 256행, 직렬화 writer는 최대 2행을 추가한다. 행은 2,048바이트
이하로 제한한다. 직렬화 완료는 임시 응답 파일을 모두 쓴 시점이며, 그 뒤 최종 파일명으로
rename한다. 계측은 추가 할당/파일 I/O를 발생시키므로 무계측 성능과 동일하지 않다.
직렬화 지점에는 response_ok를 기록해 정상 program 응답과 오류 응답을 구분한다.

Python은 성공 응답 또는 세션 정리 전에 최대 258행을 수집한다. 비정상 종료 시
마지막 불완전 행을 제외한 완전 행들을 보존한다. 파일은 세션 정리 때 제거되며 검증
도구는 `summary.json`의 `jeb_phase_trace`에 스냅샷을 저장한다. 마지막 기록 이후의
진행을 단정하거나 기록이 없다는 이유만으로 해당 단계에서 충돌했다고 결론내리지 않는다.
OOM 상황에서는 계측 기록 자체가 실패할 수 있다.

테스트는 기록/행 수 제한, 선택적 기록 실패, 찢어진 마지막 행, 정리 후 보존을 확인한다.
실제 JEB 작은 fixture에서는 선언 완료·인덱스 완료·직렬화 시작의 존재를 확인했다.
캐시 키에 PhaseTrace 소스 해시를 넣어 변경 전 캐시로 새 시험을 대체하지 않는다.

## amoremall 실제 관측

`build/large-apk-20261004-phases/amoremall/summary.json`에 24개 체크포인트를 보존했다.
힙 2GiB/본문 내보내기 8MiB, 시간 180초/RSS 4GiB/시스템 여유 1GiB guard 조건이었다.
약 56.3초에 JVM이 명시적인 OutOfMemoryError로 종료했다. 기본 APK 부분 결과는 저장됐지만
DEX 메서드 수는 0이며 전체 분석은 미완료다. 임시로 내보낸 본문은 정상 응답이 없어 복구하지 않았다.

artifact open 시작 heap used는 74,366,208바이트, 완료 시 1,988,587,160바이트였다.
후자는 heap max 2,147,483,648의 약 92.6%다. 클래스 42,032개/필드 166,448개 목록
수집 후 관측 heap used는 2,047,567,472바이트였다. 이 차이를 목록의 정확한 보유 크기로
해석하지 않는다. JEB가 보고한 DEX unit은 1개였으며 원본의 DEX 파일 5개와 동일한 단위가 아니다.

본문 2,836개, 8,377,509바이트에서 내보내기 한도에 도달한 뒤에도 선언 수집은 계속됐다.
마지막 기록은 메서드 선언 180,000개 시점: heap used 2,140,577,272바이트,
GC 누적 160회/11,608ms였다. artifact open 완료의 GC 누적은 83회/1,567ms였다.
index_done/response_serialization_start 기록은 없다. 정상 소형 fixture에서는 해당
단계 기록이 있으므로 계측 자체의 존재를 확인했다. 다만 OOM 이후 마지막 기록 유실
가능성까지 배제할 수는 없다. 이번 실행에서 응답 직렬화의 메모리 비용은 측정하지 못했다.

관측은 JEB artifact 처리 시 이미 높은 힙 점유와 후속 선언 수집 중 추가 압박을 보여준다.
직렬화만 고치면 해결된다는 근거는 없다. 다음 작업은 클래스/필드/메서드 선언 인덱스의
개수·메모리 예산과 부분 결과 의미를 설계·구현하는 것이다. 작은 예산이라도 기본 JEB
artifact 처리 비용 자체는 남으므로 완료를 보장하지 않는다.

마지막 수정 후에는 관련 17개(JEB 포함)를 다시 통과했다.
