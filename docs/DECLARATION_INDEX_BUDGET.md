# 선언 인덱스 예산과 부분 결과 (2026-10-04)

기본값은 클래스/필드/메서드 종류별 20,000개 항목, 합산 인코딩 계수 8MiB다.
`Settings.max_index_entries`는 1~200,000, `max_index_mib`는 1~64 정수이며
기존 설정 파일에 필드가 없으면 기본값을 적용한다. 큰 APK의 기존 무제한 선언 수집과
동작이 달라질 수 있다. CLI `--max-index-entries`, `--max-index-mib` 또는 settings.json으로
조정한다. 전용 GUI 설정 입력란은 아직 없으며 GUI 분석도 저장 설정값을 사용한다.

종류별 제한은 DEX unit 전체를 합산한다. 기본 native 정책은 JEB 순서대로 앞부분을 수집한다.
후속으로 선택적 unit 내부 Manifest/package 우선 정책을 추가했다(`INDEX_PRIORITY.md`).
클래스는 class_index/classes/상속 맵, 필드는 field_index/fields를
함께 반영하거나 함께 제외한다. 메서드 인덱스에 포함되지 않은 본문은 내보내지 않는다.
참조 항목도 인덱스 한도에 포함되므로 항목 수가 앱에 정의된 고유 메서드 수는 아니다.

바이트 예산은 각 행의 관련 인덱스/목록/상속 필드를 담은 ASCII JSON 직렬화 길이와 개행으로
계수한다. 실제 응답 파일 크기나 RSS의 상한은 아니며 Manifest, DEX unit 요약, 진단과
JEB 내부 데이터는 제외된다. 바이트 한도에 처음 걸리면 나머지 종류도 수집하지 않는다.
개수 한도만 걸렸다면 다른 종류는 남은 바이트 예산 안에서 계속 수집한다.
단일 시그니처를 읽고 인코딩하는 순간 비용과 JEB artifact 처리의 기본 비용은 남는다.

종류별 제외 항목 수, 계수 바이트, 한도 및 상속/참조 불완전 가능성을 진단에 남긴다.
정상 응답은 이미 수집한 본문과 메타데이터를 보존하고 complete=false로 저장된다.
누락 항목을 근거로 대상 API/위험이 없다고 결론내리면 안 된다. 설정값은 provenance와
캐시 키에 포함한다. 작은 예산에서 큰 예산의 캐시를 재사용하지 않는다.

## 실제 amoremall 검증

힙 2GiB, 본문 내보내기 8MiB, 종류별 인덱스 1,000개/합산 계수 1MiB,
시간 180초·합산 RSS 4GiB·시스템 여유 1GiB guard로 시험했다.
`build/large-apk-20261004-index1000/amoremall/summary.json`에 결과가 있다.

분석 21.437초, 근거 확인/저장까지 49.567초였다. 클래스·필드·메서드 인덱스 각각 1,000개,
본문 959개를 정상 응답으로 받았다. 계수 크기는 565,491바이트였고 개수 한도에 의해
클래스 41,032개, 필드 165,448개, 메서드 항목 285,211개가 제외됐다.
합산 RSS 피크는 2,564,546,560바이트(약 2.39GiB)이며 강제 종료 없이 JEB를 닫았다.
index_done과 정상 응답 직렬화 시작/완료 체크포인트를 확인했다.

프로젝트는 2,189,114바이트로 저장 후 재열기까지 성공했다. complete=false, 본문 959개와
제외 진단이 보존됐다. finding 48개는 이 제한된 범위의 분석 결과이며 새 취약점 48개라는
뜻이 아니다. 두 메서드의 JEB 소스/AST/XREF/CFG 조회를 확인했고 그중 하나의 AST 호출
오프셋 1개가 DEX 오프셋과 일치했다. 전체 앱 또는 모든 finding의 검증은 아니다.

이번 결과는 **대형 APK의 제한된 부분 분석·저장·재열기 성공**이며 전체 분석 성공이 아니다.
종류별 1,000개 설정으로 시험했으므로 기본 20,000개나 다른 기기의 성능도 보장하지 않는다.
